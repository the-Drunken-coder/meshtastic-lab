message reached at least one receiver. `Receiver delivery` counts every possible
receiving node, which is the more informative metric for full-mesh broadcasts.

## Interpretation

The API scheduler handled far more load than the firmware and radio path. At the
full 10,000-message ceiling, scheduling completed without a crash. Memory stayed
near 151 MiB and event-loop lag remained around 10 ms. The native firmware and
LoRa channel could not absorb that offered rate. Only 2.56% of requests were
admitted, 2.04% reached RF, and 1.06% reached any receiver.

The 10-radio synchronized-burst case is harsh even at three messages per minute
per source. Receiver delivery stayed below 23% in all six profile trials. This is
not a general claim that a 10-radio network is unusable. The baseline generator
aligned every source on the same ticks, making this a repeatable worst-case
contention test. The improved harness now preserves that case and adds seeded
source phases for comparison.

`SHORT_FAST` reduced the median latency by about 6.9 times and cumulative airtime
by about 12.2 times relative to `LONG_FAST` in that burst test. It did not clearly
improve delivery. It delivered slightly more receiver opportunities in the median
trial but fewer unique messages. More repeated trials with the new de-synchronized
schedule are required before ranking profiles by reliability.

The four-hop line proved real firmware relaying and acknowledgments, but the cost
was high. Each delivered direct message required ten RF transmissions, and median
latency was 23.4 seconds.
The partition test showed retry behavior, not store-and-forward behavior. Restoring
the link did not resurrect the message sent while disconnected.

These are text-message tests with payloads up to 200 bytes. They do not measure a
fragmented file-transfer or streaming data plane, and the simulator does not model
terrain, antennas, fading, batteries, or physical radio timing.

## Operational assessment

The supported setup path worked. The cached exact-head image rebuild took 9.0
seconds; I did not measure a cold firmware build. Every run records exact build
provenance. The API, scenario replacement, live metrics, native firmware events,
and full exports were enough to run the experiments without changing the firmware
path. Ten native nodes started in about 21 seconds on this machine.

Problems found in the baseline:

1. A terminal traffic status could become visible just before the export was ready.
   The 10,000-message run returned `409 Conflict` on the first export request, then
   succeeded moments later. The original runner had to retry this transition.
2. Multi-source traffic started every source at tick zero. The API needed
   explicit burst, fixed-phase, jittered, and Poisson schedules.
3. `delivered` can make broadcasts look healthier than they are. Receiver delivery
   ratio should be the primary broadcast result.
4. `link-disabled` is counted as a drop for every non-neighbor in a sparse graph.
   The successful four-hop test showed 47 such drops. Topology exclusions should
   be separated from actual loss.
5. A direct message can record `MAX_RETRANSMIT` and later deliver and acknowledge.
   Transient routing events need to be separate from each message's final outcome.
6. Long drain periods exposed no useful progress reason. The partition run looked
   idle for nearly five minutes while one message remained unresolved.
7. Repeated clean starts observed only part of the expected NodeDB graph during
   warm-up, including 19 of 90 pairs in one `LONG_FAST` start and 64 of 90 in one
   `SHORT_FAST` start. Trial exports need a NodeDB readiness snapshot so readers
   can see the starting state.
8. Expected one-shot client teardown produced at least 35 broken-pipe error logs
   and 34 tracebacks during this session. Clean shutdown should not look like a
   runtime failure.
9. Ten radios is a hard product ceiling because the public endpoint range is fixed.
   Larger density work will need optional headless nodes or dynamic endpoint
   allocation instead of a required host port per simulated radio.

## Follow-up improvements applied

I implemented and verified the four highest-value harness and lifecycle changes:

1. Terminal traffic state and export readiness are now one invariant. The
   controller keeps the run in `FINALIZING` phase while it clones, serializes, and
   persists the result, then publishes the terminal state. A blocking-persistence
   regression test confirms the live summary remains non-terminal and the export
   remains unavailable until the file is committed. The improved real-system
   runs retrieved both exports on the first request after terminal status.
2. Traffic requests now accept `sourceTiming`: `aligned`, `evenly-staggered`, or
   `deterministic-jitter`. Destination choice, packet identifiers, and source
   timing use separate seeded streams. The bench runner now compares aligned and
   jittered contention and supports named subsets plus 1 to 10 repetitions with
   median, minimum, and maximum aggregates.
3. Live summaries now report `phase`, `pendingFirmwareAdmissions`,
   `unresolvedDirectMessages`, and `drainDeadlineSecondsRemaining`. In the
   improved four-hop run, the API visibly changed from `GENERATING` to `DRAINING`,
   reported one unresolved direct message and a 236.6-second maximum horizon,
   then reported zero unresolved at 38.2 seconds and completed at 57.1 seconds.
4. One-shot official-client connections now install their shutdown guard before
   connecting. This prevents a late config-complete frame from starting a
   heartbeat on a half-closed socket. A fresh three-node acceptance lifecycle
   went from two broken-pipe incidents before the final fix to zero broken-pipe,
   traceback, or lowercase broken-pipe log matches after it. Acceptance still
   passed with three official clients, relay removal and restoration, traffic,
   persistence, and listener cleanup.

The first aligned-versus-jittered `LONG_FAST` comparison was deliberately only a
smoke trial. Aligned source starts spanned 0.002 seconds and delivered 10 of 20
messages, with 33.33% receiver delivery and 5.42-second median latency. Seeded
jitter spread starts across 19.018 seconds and delivered 11 of 20, with 33.89%
receiver delivery and 3.35-second median latency. That is a small improvement,
not enough evidence to claim a general reliability win. The jittered run's final
native failed-reception sample was incomplete, so its zero failed-reception count
must not be compared with the aligned run's count.

## Changes I would make next

1. Add deterministic Poisson traffic and confidence intervals on top of the new
   repeated-trial harness.
2. Separate offered, admitted, transmitted, uniquely delivered, receiver-delivered,
   and finally failed outcomes in the primary UI. Keep topology exclusions and
   transient routing events out of the final-failure bucket.
3. Record the final drain exit reason, in addition to the new live counts and
   deadline, in completed summaries.
4. Add a headless-node mode so the same medium and firmware path can be exercised
   at 20, 50, or more radios without publishing a TCP port for every node.
5. Add a separate fragmentation/file-transfer workload before using this tool to
   make claims about bulk data throughput.
